Client: Browser / CLI

Nơi bạn gõ câu hỏi. Gửi HTTP request và nhận kết quả streaming qua SSE — từng token hiện ra ngay khi model sinh. Không phải tầng phần mềm của server, nhưng là điểm đầu và cuối của mọi request.

Tầng C: Go Server

API server — OpenAI /v1/chat/completions, internal canonical format + thin adapter, streaming qua SSE, multi-user session trong RAM.

Agentic loop — khi model trả tool_use, Go execute tool → gửi tool_result lại model → lặp tối đa 10 vòng cho tới end_turn. Mỗi inference call đi qua BatchScheduler.Submit() để được gom batch.

Tầng B: gRPC Bridge

Proto định nghĩa InferenceService.Generate() (single, token streaming) và BatchInferenceService.BatchGenerate() (batch, mỗi event kèm request_id để route). Cancel propagation qua context — batch mode hỗ trợ cancel từng request riêng.

Tầng A: Inference Engine

Python worker chạy trên GPU (RTX 3060 12GB). Hai chế độ: InferenceEngine.generate() cho single request với token-level streaming, và BatchEngine.generate_batch() cho batch requests với model.generate() padded inputs — xử lý nhiều request trong 1 GPU pass.

2. Inference: Từ text đến token

2.1 Tokenization & Embedding

Mỗi văn bản được cắt thành tokens — đơn vị nhỏ nhất model hiểu được. Một token ~ 0.75 từ tiếng Anh, ~ 0.5 từ tiếng Việt.

Tokenizer dùng thuật toán BPE (Byte-Pair Encoding): bắt đầu từ các ký tự đơn, lặp đi lặp lại gộp cặp phổ biến nhất. Kết quả: từ điển ~150K tokens.

Ví dụ tokenization
"Xin chào, tôi là AI"
→ ["Xin", " ch", "ào", ",", " t", "ôi", " là", " AI"]
→ [12481, 891, 3721, 11, 421, 2083, 671, 9984]
→ Mỗi số → embedding vector 2048 chiều
// Embedding = số hóa ý nghĩa: hai token giống nghĩa có vector gần nhau

2.2 Attention — cách model "đọc" context

Mỗi token mới sinh ra cần nhìn lại toàn bộ các token trước đó để hiểu ngữ cảnh. Cơ chế: mỗi token tính Query (Q) của chính nó, so khớp với Key (K) của tất cả token cũ để tìm ra token nào liên quan, rồi tổng hợp Value (V) của chúng.

// Attention cho 1 head, 1 token mới
for mỗi token cũ i trong lịch sử:
    score[i] = Q_mới · K_i / √d    // dot-product similarity
weights = softmax(scores)          // chuẩn hóa → tổng = 1
output = Σ(weights[i] × V_i)       // tổng có trọng số

GQA (Grouped Query Attention): Qwen 2.5 Coder dùng 28 query heads nhưng chỉ 4 KV heads. Mỗi 7 Q-heads share chung 1 cặp (K,V). → KV cache nhẹ hơn 7× so với multi-head attention truyền thống.

2.3 KV Cache — linh hồn của serving

Mỗi lần sinh token, model không thể tính lại attention từ đầu (quá chậm, O(n²) mỗi step). Thay vào đó, K và V của mỗi token cũ được lưu lại trong VRAM. Token mới chỉ cần tính (K,V) của chính nó rồi nối vào cache.

// Không có KV cache: O(n²) mỗi step
Step 1: tính attention(1 token)         → 1² ops
Step 2: tính attention(2 tokens)        → 2² ops
...
Step N: tính attention(N tokens)        → N² ops
// Tổng: 1² + 2² + ... + N² ≈ N³/3

// Có KV cache: O(n) mỗi step
Step 1: tính (K₁,V₁), cache lại         → 1 op
Step 2: tính (K₂,V₂), attention vs K₁,V₁ → 2 ops
...
Step N: tính (Kₙ,Vₙ), attention vs cache → N ops
// Tổng: 1 + 2 + ... + N ≈ N²/2   ← Nhanh hơn N lần!
Tham sốGiá trịGiải thích
Layers28Mỗi layer có KV cache riêng
KV heads4 (GQA 28:4)Giảm 7× so với MHA
Head dim128Kích thước mỗi head
Byte per element2 (bfloat16)FP16 / BF16 precision
KV / token57,344 bytes = 0.057 MB28 × 4 × 2 × 128 × 2
KV @ 8K context470 MBChỉ 3.8% VRAM
← token cũ (đã cache)   |   token mới (đang tính)

Trên production (H100): KV cache là bottleneck chính. Model 100B+ với 128K context có thể cần 50-100GB chỉ cho KV cache. vLLM giải quyết bằng PagedAttention — quản lý KV cache theo block giống như OS quản lý virtual memory pages.

2.4 Prefill vs Decode — hai pha của inference

Pha 1: PREFILL (1 lần)
Xử lý toàn bộ prompt tokens cùng lúc
→ tính K,V cho từng prompt token
→ lưu vào KV cache
→ sinh token đầu tiên

Compute-bound (tận dụng GPU)
O(n²) nhưng chạy 1 lần
Pha 2: DECODE (lặp N lần)
Mỗi bước sinh 1 token mới
→ tính (K,V) cho token mới
→ attention với toàn bộ KV cache
→ nối vào cache

Memory-bound (đọc KV cache)
O(n) mỗi step, lặp N lần → O(N²)

Ý nghĩa cho serving: Với prompt ngắn (chat), prefill rất nhanh (~60ms). Thời gian chủ yếu là decode (~60ms × N tokens). Với prompt dài (RAG với context 32K trang), prefill có thể chiếm 1-3 giây. Đây là lý do prefix caching quan trọng: cache K,V của system prompt để không phải prefill lại mỗi request.

3. Serving: Từ 1 request đến hàng nghìn

3.1 Streaming — token-level real-time

Thay vì đợi model sinh xong toàn bộ response rồi mới gửi về (có thể mất 20-30 giây), server gửi từng token một ngay khi nó được sinh ra.

// Chain streaming trong AI Factory
GPU sinh token → yield token
    ↓
Python gRPC stream.send(token)    // server-streaming
    ↓
Go for event := range stream.Recv()
    ↓
SSE: "data: {\"delta\":{\"text\":\"Xin\"}}\n\n"
    ↓
Browser EventSource / fetch reader
    ↓
// Token hiện ra từng chữ một trên màn hình

gRPC server-streaming (Python → Go) cho phép Go cancel giữa chừng bằng cách hủy context. Python phát hiện context.cancelled() → dừng inference → giải phóng KV cache.

SSE (Go → Browser) là HTTP protocol đơn giản nhất cho streaming. Mỗi token là 1 event. Kết thúc bằng data: [DONE]. Không cần WebSocket vì stream là 1 chiều.

3.2 Batching — gom nhiều request vào một GPU pass Đã implement

Bài toán: GPU mạnh nhất khi xử lý nhiều request cùng lúc (batch). Nhưng các request đến không cùng thời điểm và có độ dài khác nhau. Làm sao để không request nào phải đợi?

Trước: Inference Queue (serial)
Mỗi request chạy tuần tự, chờ slot
A: ████████ 2.0s B: ----████████ 4.0s
C: --------████████ 6.0s

B,C phải đợi (lãng phí 50-66% thời gian)
GPU idle giữa các request
Sau: Batch Scheduler (implemented)
Gom request trong cửa sổ 100ms
Batch [A,B,C]: ████████ 1.8s A: ████████ 1.79s
B: ████████ 1.80s (+0%)
C: ████████ 1.79s (+0%)

3 requests cùng 1 GPU pass
Latency giảm 3.9× cho request cuối 
// Batch Scheduler — Go implementation
type BatchScheduler {
    submitCh     chan *batchItem       // nhận request từ handler
    maxBatchSize 4                   // giới hạn bởi VRAM
    batchWindow  100ms               // cửa sổ gom request
}

// collectorLoop — heart của scheduler
for {
    first := <-submitCh               // block đợi request đầu tiên
    batch := []{first}

collect:
    for len(batch) < maxBatchSize {
        select {
        case req := <-submitCh:       // gom thêm trong 100ms
            batch = append(batch, req)
        case <-timer.C:              // hết giờ → dispatch
            break collect              // thoát vòng gom, dispatch ngay
        }
    }

    go dispatchBatch(batch)          // gửi qua gRPC BatchGenerate
}

Go BatchScheduler: Gom request 100ms → dispatch 1 gRPC BatchGenerate → Python BatchEngine model.generate(batch=[A,B,C]) với padding (thêm token rỗng vào câu ngắn cho cùng độ dài) + attention mask (báo model token nào là thật để không tính token rỗng) → decode từng token riêng → stream kèm request_id → route về đúng channel.

Hiện tại: Static Batch. Batch cố định sau khi dispatch — không thêm/bớt request giữa các decode step. Tuần 7-8 sẽ nâng cấp lên dynamic continuous batching: tự quản lý KV cache per-request, thêm request mới sau prefill, bỏ request đã sinh token kết thúc (EOS — end-of-sequence) hoặc hết max_tokens giữa các step.

Kết quả benchmark: batch=4 (4 requests cùng lúc) đạt 66 tok/s — gấp ~3.9× so với chạy single (~17 tok/s). GPU xử lý nhiều request trong cùng một forward pass thay vì từng cái riêng lẻ.

3.3 Agentic Loop — khi model tự gọi công cụ

Điểm khác biệt giữa "chatbot" và "AI agent": model không chỉ trả lời, mà còn tự quyết định gọi tool (đọc file, chạy lệnh, tìm kiếm) rồi dùng kết quả để trả lời chính xác hơn.

// Agentic loop — simplified
func AgenticLoop(session, userMessage):
    session.Add(userMessage)

    for iteration := 0; iteration < 10; iteration++:
        events = inference.Generate(session.Messages)

        for event := range events:
            if event.Type == "token":
                streamToClient(event.Token)        // real-time
            else if event.Type == "tool_use":
                result = executeTool(event.Name, event.Args)
                session.Add(ToolResult{result})
                break                            // loop lại → model xử lý kết quả
            else if event.Type == "end_turn":
                return                            // done

OpenAI tool format: model gọi tool qua tool_calls array với function.arguments JSON string. AI Factory dùng internal canonical format — adapter chuyển về một kiểu chung.

3.4 Context Window Management

Context window có giới hạn (8K tokens trong project này). Khi vượt quá, phải cắt bớt tin nhắn cũ — nhưng không được cắt giữa cặp tool_use/tool_result.

// Truncation algorithm — Go session manager
func TruncateMessages(msgs, maxTokens):
    // 1. Đếm token từ cuối lên, tìm điểm cắt
    keepFrom = len(msgs)
    for i := len(msgs)-1; i >= 0; i--:
        if estimated + msgTokens[i] > maxTokens:
            keepFrom = i+1; break
        estimated += msgTokens[i]

    // 2. Bảo vệ tool_use/tool_result pairs
    if msgs[keepFrom].Role == "tool":
        // Tìm tool_use tương ứng, giữ lại cả cặp
        keepFrom = findMatchingToolUse(msgs, msgs[keepFrom])

    // 3. Bỏ tool_use mồ côi ở cuối
    if lastMsg có tool_call nhưng không có tool_result:
        remove(lastMsg)

    return msgs[keepFrom:]

3.5 Cancel Propagation — dừng inference từ xa

Khi user đóng tab browser, inference vẫn đang chạy trên GPU — lãng phí compute và VRAM. Cancel propagation đảm bảo tín hiệu hủy được truyền xuyên suốt chain.

Client disconnect
    ↓ r.Context().Done()
Go context.Cancel()
    ↓ ctx.Done() trong agentic loop
gRPC stream bị cancel
    ↓ context.cancelled() trong Python
Python cancel_event.set()
    ↓ engine.generate() check cancel_event
Dừng generation, yield STOP_CANCELLED
    ↓
Giải phóng KV cache

Trong production: Đây là tính năng bắt buộc. Không có cancel propagation = GPU lãng phí hàng nghìn giờ mỗi ngày cho các request bị abandon. vLLM/TensorRT-LLM đều có built-in abort mechanism.

Chạy trên RTX 3060 12GB, model Qwen 2.5 Coder 7B (4-bit NF4).

Bottleneck chính: TPOT ~60ms. RTX 3060 có memory bandwidth ~360 GB/s, trong khi H100 có ~3.35 TB/s — gấp gần 10×. Decode phase là memory-bound (đọc KV cache), nên bandwidth quyết định tốc độ token/s. Đây là giới hạn phần cứng, không phải lỗi thiết kế.

5. Lộ trình học tập

Mỗi giai đoạn thay thế một module dùng sẵn bằng code tự viết — "dùng trước, thay sau".

  • Tuần 1–2 Dùng toàn bộ HuggingFace. Focus: proto → gRPC → Go server → model chạy end-to-end. OpenAI /v1/chat/completions, SSE streaming, multi-turn agentic loop. Done
  • Tuần 1–2 Batching (static): BatchScheduler + BatchEngine + BatchInferenceService gRPC. Gom request 100ms, dispatch batch, route token per request_id. Done
  • Tuần 3–4 Tự implement tokenizer: BPE encode/decode từ tokenizer.json. Hiểu special tokens, chat template. Inference
  • Tuần 5–6 Tự implement sampling: greedy, temperature, top-p, top-k, beam search. Thay thế model.generate(). Inference
  • Tuần 7–8 Tự quản lý KV cache + dynamic continuous batching: thêm/bớt request giữa các decode step. Hiểu memory layout, PagedAttention cơ bản. Bước quan trọng nhất để hiểu vLLM. Serving
  • Tuần 9+ Optional: Tự viết forward pass (embed → attention → FFN — feed-forward network — → unembed — chọn token kế tiếp). Thay toàn bộ model.forward(). Optional
  • Sau đó Prefix caching: cache K,V của system prompt. Giảm TTFT 90% cho multi-turn conversations. Advanced
